# Migration notes for 0.19.0

## Browser gateway UI

The gateway now serves the SolidJS single-page application by default. It keeps
the existing gateway URL and API contracts. If the browser has no valid token
for the new UI, enter the value of `GATEWAY_AUTH_TOKEN` at the sign-in prompt.
The UI stores that token in browser session storage. A one-time link such as
`/chat?token=<token>` can also complete sign-in. The UI removes the token from
the address bar before probing the gateway, even if validation then fails.

The previous shell remains available during the rollback window. To use it for
an operator session, set `AXINITE_WEB_UI=legacy` in the gateway environment and
restart the process; the choice is read at startup. The default SolidJS UI
restores the logs route, gateway restart control, attestation display,
extension pairing controls, chat media and auth cards, and job detail tabs.

## Feature flag overrides

The gateway adds deployment-scoped feature flag overrides. Existing
`FEATURE_FLAG_<NAME>` environment variables remain supported and take
precedence over stored overrides. Operators can write an override through the
authenticated settings endpoint using `PUT /api/settings/feature_flag:<name>`
with an `X-Deployment-Id` header and a JSON `value` boolean. Reads use
`GET /api/features`; an absent deployment header selects `default`, while
writes require a valid deployment header. The SPA currently uses the `default`
deployment; API clients selecting another deployment must send the same header
on reads and writes. See the [user's guide](../users-guide.md#feature-flags)
for the accepted header and value formats.

The new override table is additive for PostgreSQL and libSQL. Existing settings
remain unchanged, and no manual data migration is required beyond the gateway's
normal startup migrations.

## Configuration environment snapshots

Configuration resolution now runs from an explicit `EnvContext` snapshot
captured once at startup. A SIGHUP hot reload starts each cycle from that
snapshot and applies injected secrets; it does not reread process environment
variables or `.env` files. Environment-backed settings, including `HTTP_HOST`
and `HTTP_PORT`, keep their startup values until the process restarts. To
change them, update the service environment and restart Axinite. Reload applies
only the HTTP webhook settings: it restarts or stops the listener when the bind
address or `channels.http` presence changes, and pushes a rotated
`HTTP_WEBHOOK_SECRET` to live channels. Reload can only drive the listener
controller that startup created, so when startup registered no webhook routes
SIGHUP cannot start an HTTP listener; enabling one takes a restart. A non-empty
`HTTP_WEBHOOK_SECRET` in the startup environment outranks the injected secret,
so a rotated store secret does not reach live channels while that override is
set: remove the override and restart to rely on store-backed rotation. Other
resolved fields, including database-backed settings, are discarded until the
process restarts.

This is a behaviour change for operators who relied on editing `.env` and
signalling SIGHUP to pick up environment changes. See the
[user's guide](../users-guide.md#configuration-reload) for the reload contract.

Library embedders and tests that previously called `std::env::set_var` before
building configuration should construct an `EnvContext` with
`EnvContext::default().with_env(...)`. To load `settings.json` and the default
TOML overlay, call `Config::from_env_from_context(...)`. For an explicit TOML
path, load `settings.json` from the snapshot's base directory and pass the
settings, snapshot, and path to `Config::from_context_with_toml(...)`.
`Config::from_context(...)` resolves the settings it is given and does not load
files; put the resulting `Config` in `AppBuilderParams` and pass it with the
same snapshot to `AppBuilder::new_with_context(...)`. The ambient
`Config::from_env()` and `Config::from_env_with_toml(...)` entry points remain
for early startup paths that genuinely own the capture. `clippy.toml` does not
disallow these wrappers, only the underlying `std::env` and `dotenvy` calls, so
calling them outside a capture boundary is a review-time convention rather than
a lint failure.

Library embedders should use `HotReloadManager::new_with_context(...)` (or
`AppBuilder::new_with_context(...)`) so each reload starts from the caller's
explicit snapshot. `HotReloadManager::new(...)` captures the ambient
environment and is intended for early startup only.

The remaining context-aware entry points follow the same rule:

- `ConfigLoader::load(&self, ctx: EnvContext)` and
  `SecretInjector::inject(&self, ctx: &mut EnvContext)` receive the snapshot
  for the current reload cycle. Implementations of either trait must resolve
  their inputs from that argument and must not fall back to the process
  environment; call sites must pass the snapshot they already hold rather than
  capturing a new one.
- `setup_wasm_channels_from_context(WasmChannelSetupRequest { env_context, .. })`
  replaces the positional `setup_wasm_channels(...)` entry point and resolves
  channel credential fallbacks from that snapshot. Callers pass one request
  struct: `config`, `secrets_store`, `extension_manager`, `database`, and
  `env_context`.
- `ExtensionRegistry::new_with_catalog(catalog_entries, relay_url)` takes the
  snapshot's relay URL as a second argument. `Some` seeds a channel-relay entry
  carrying that URL; `None` seeds no channel-relay entry, regardless of ambient
  configuration. `ExtensionRegistry::new()` therefore no longer includes the
  relay entry, so a caller that relied on an ambient `CHANNEL_RELAY_URL` must
  pass the snapshot value explicitly.
- `extensions::registry::builtin_entries()` is replaced by
  `builtin_entries_with_relay(relay_url)`; pass `None` when no relay is
  configured. The removed function captured `CHANNEL_RELAY_URL` itself.
- `OpenClawImporter::detect_from(&EnvContext)` inspects an explicit snapshot;
  the ambient `OpenClawImporter::detect()` remains only for callers that own
  the capture. Both now return `std::io::Result<Option<PathBuf>>`, so a caller
  must distinguish `Ok(None)` (no OpenClaw installation) from `Err` (the
  candidate directory or file could not be queried) instead of treating every
  failure as an absent installation.
- `setup::check_onboard_needed(&EnvContext)` takes the snapshot instead of
  reading the process environment, and `PidLock::acquire_in(&Path)` acquires
  the lock inside an explicit base directory. Callers that previously relied on
  the ambient variants should pass the snapshot and base directory they already
  hold.

Two runtime types now carry the snapshot instead of reading the process
environment when they are used:

- `RestartTool` is no longer a unit struct. It holds the `EnvContext` it
  resolves `AXINITE_IN_DOCKER` and `AXINITE_DISABLE_RESTART` from.
  `RestartTool::new()` captures the ambient environment at the owning startup
  boundary, `RestartTool::from_context(env)` takes the snapshot a caller
  already holds, and `Default` delegates to `new()`. A struct literal
  `RestartTool` no longer compiles; call `new()` or `from_context()`.
- `GatewayState` gains the public `env_flag_overlay` field, which holds the
  `FEATURE_FLAG_<NAME>` values resolved from the startup snapshot.
  `GatewayChannel::new_from_context(config, env_context)` populates it from the
  snapshot a caller supplies. Code that constructs `GatewayState` directly,
  such as a gateway test harness, must add the field; when the environment
  defines no known flags, `Default::default()` matches the empty overlay.

## Settings file errors are reported

Startup now reports an unreadable or malformed `settings.json` instead of
silently replacing it with defaults, and a reload reports the same error when
it runs from a snapshot-backed deployment that reads the file. A missing file
still yields defaults, so first runs and fresh installations are unaffected.

A deployment whose `settings.json` exists but cannot be read, or is not valid
JSON, now fails configuration loading with
`failed to read settings file <path>: <reason>` or
`failed to parse settings file <path>: <reason>`. Startup stops. In a
snapshot-backed deployment a reload keeps the previous configuration running
and logs the same message; a database-backed deployment reloads from the
settings table and `config.toml` and does not inspect `settings.json`. Correct
the permission or syntax problem, restore the file from backup, or remove it to
fall back to defaults.

The file location is `settings.json` under the Axinite base directory
(`~/.axinite` by default, or `AXINITE_BASE_DIR` when set). See the
[user's guide](../users-guide.md#settings-file) for the supported recovery
steps.

## Reliability telemetry

Startup configuration loading, hot reload, secret injection, and WASM channel
credential handling now emit reliability counters behind the existing optional
`metrics` feature:

- `axinite.startup.config_load` with `outcome` = `success` | `settings_error` |
  `config_error`.
- `axinite.reload.outcomes` with `outcome` = `success` | `http_removed` |
  `config_error` | `listener_error`.
- `axinite.reload.secret_injection` with `outcome` = `injected` | `missing` |
  `retained_after_error` | `error`.
- `axinite.wasm.channel_credentials` with `outcome` = `injected` | `partial` |
  `missing` | `list_error` | `decryption_error`. `partial` means a channel
  declared several credentials and only some of them resolved.

No recorder or exporter is bundled with the feature, so enabling it without
installing a recorder drops the counters. Non-success outcomes also log at
`info` through `tracing`, with no secret values or paths, so failures remain
visible at the default log level without the feature. See the developer's guide
[reliability metrics](../developers-guide.md#reliability-metrics)
section for the labels and emission rules.

## Removed self-repair feature

The obsolete `self_repair_extras` Cargo feature has been removed. Source builds
that list this feature in Cargo commands or build configuration must remove it.
Automatic broken-tool rebuilding remains unwired in production, so removing the
feature does not disable a production repair capability.

## Source-build toolchain

Development builds from a source checkout now use the pinned
`nightly-2026-10-16` toolchain, `-Zthreads=8`, and `mold` on Linux. Before
building, source builders must install the pinned linker and expose its install
directory to bare Cargo commands:

```sh
make install-build-tools
export PATH="$HOME/.local/bin:$PATH"
```

The installer places `mold` in `$HOME/.local/bin`; Linux `clang` must be
installed separately with the system package manager. Make targets add the
build-tool directory to `PATH` automatically, so the export is needed for bare
`cargo build`, `cargo test`, and `cargo check` commands.

The development flags do not apply to release and packaging builds, coverage,
Docker, Whitaker, or the MSRV check. Docker images use the stable `rust:` base
images specified by their Dockerfiles, and the MSRV check uses stable Rust
1.95. Release and coverage routes set their own `RUSTFLAGS`, and Whitaker keeps
its warning-only `RUSTFLAGS` assignment.
