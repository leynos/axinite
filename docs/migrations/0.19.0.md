# Migration notes for 0.19.0

## Browser gateway UI

The gateway now serves the SolidJS single-page application by default. It keeps
the existing gateway URL and API contracts. If the browser has no valid token
for the new UI, enter the value of `GATEWAY_AUTH_TOKEN` at the sign-in prompt.
The UI stores that token in browser session storage. A one-time link such as
`/chat?token=<token>` can also complete sign-in. The UI removes the token from
the address bar before probing the gateway, even if validation then fails.

The previous shell remains available during the rollback window. To use it for
an operator session, set `AXINITE_WEB_UI=legacy` in the gateway environment and
restart the process; the choice is read at startup. The default SolidJS UI
restores the logs route, gateway restart control, attestation display,
extension pairing controls, chat media and auth cards, and job detail tabs.

## Feature flag overrides

The gateway adds deployment-scoped feature flag overrides. Existing
`FEATURE_FLAG_<NAME>` environment variables remain supported and take
precedence over stored overrides. Operators can write an override through the
authenticated settings endpoint using `PUT /api/settings/feature_flag:<name>`
with an `X-Deployment-Id` header and a JSON `value` boolean. Reads use
`GET /api/features`; an absent deployment header selects `default`, while
writes require a valid deployment header. The SPA currently uses the `default`
deployment; API clients selecting another deployment must send the same header
on reads and writes. See the [user's guide](../users-guide.md#feature-flags)
for the accepted header and value formats.

The new override table is additive for PostgreSQL and libSQL. Existing settings
remain unchanged, and no manual data migration is required beyond the gateway's
normal startup migrations.

## Source-build toolchain

Development builds from a source checkout now use the pinned
`nightly-2026-10-16` toolchain, `-Zthreads=8`, and `mold` on Linux. Before
building, source builders must install the pinned linker and expose its install
directory to bare Cargo commands:

```sh
make install-build-tools
export PATH="$HOME/.local/bin:$PATH"
```

The installer places `mold` in `$HOME/.local/bin`; Linux `clang` must be
installed separately with the system package manager. Make targets add the
build-tool directory to `PATH` automatically, so the export is needed for bare
`cargo build`, `cargo test`, and `cargo check` commands.

The development flags do not apply to release and packaging builds, coverage,
Docker, Whitaker, or the MSRV check. Docker images use the stable `rust:` base
images specified by their Dockerfiles, and the MSRV check uses stable Rust
1.95. Release and coverage routes set their own `RUSTFLAGS`, and Whitaker keeps
its warning-only `RUSTFLAGS` assignment.
